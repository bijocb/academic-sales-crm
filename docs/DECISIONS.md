# Decision & Assumptions Register

Companion to `docs/SRS.md`. Where this register and the SRS disagree, this register wins (it records later business-owner decisions).

Status: **DECIDED** = confirmed by business owner · **ASSUMED** = default chosen by engineering, can be changed before the phase that depends on it · **OPEN** = must be answered before the phase listed.

## Decided

| ID    | Decision                                                                                                                                                                                                                                                                                                                                                                                               | Date       |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------- |
| D-001 | **Multiple organizations (multi-tenant SaaS).** Organization is the tenant. Brands, branches, teams, users and all business records belong to exactly one organization. A platform-level Super Admin sits above organizations.                                                                                                                                                                         | 2026-11-27 |
| D-002 | **Markets: India and UAE.** Time zones `Asia/Kolkata` and `Asia/Dubai`; currencies INR and AED; phone numbers normalized to E.164 (+91, +971 and others) while keeping the raw value. Time zone, currency and working week are set per brand (default from organization).                                                                                                                              | 2026-11-27 |
| D-003 | **SLA time is measured on two clocks: calendar minutes and working minutes, stored and shown separately** for every SLA instance, task and report.                                                                                                                                                                                                                                                     | 2026-11-27 |
| D-004 | **Person → Lead → Enquiry model.** Person = identity (normalized phone/email). Lead = one open sales record per person per brand (owner, stage, status, SLA, tasks). Enquiry = each inbound submission, immutable attribution (source, campaign, UTM, course interest). Brands work the same person independently. Lost / On Hold / Recovery are a **status** beside the 8-stage pipeline, not stages. | 2026-11-27 |
| D-005 | **Admission credit goes to both the first-contact executive and the closing executive.**                                                                                                                                                                                                                                                                                                               | 2026-11-27 |
| D-006 | **Admission is confirmed on the first verified payment of any amount** (advance/token included).                                                                                                                                                                                                                                                                                                       | 2026-11-27 |
| D-007 | **Refunds of advances/payments must be recorded** (a student pays an advance and later asks for the money back).                                                                                                                                                                                                                                                                                       | 2026-11-27 |

## Assumptions (engineering defaults)

| ID     | Assumption                                                                                                                                                                                                                                                                                          | Relates to    |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| A-003a | Escalation checkpoints (5/15/30/60) **fire on working minutes by default**; each SLA rule can be switched to calendar minutes. Both clocks are always recorded regardless of which one fires.                                                                                                       | D-003         |
| A-003b | A lead received outside working hours is held in the unassigned queue and allocated at the start of the next shift. Calendar clock starts at receipt; working clock starts at the next working minute.                                                                                              | D-003         |
| A-005a | "First-contact executive" = first executive to record a **connected** contact (not just an attempt). "Closing executive" = lead owner when the admission is confirmed.                                                                                                                              | D-005         |
| A-005b | Reports show **"first-contact admissions"** and **"closed admissions"** as separate metrics, each counted in full (no double-counting inside one metric). Incentive split is configurable per organization; default 50/50 when the two are different people, 100% when the same.                    | D-005         |
| A-006a | "Verified" = confirmed by payment-gateway webhook/API reconciliation or by an Accounts user's manual verification (FR-015). A browser redirect never counts. Minimum confirming amount is configurable per brand, default > 0.                                                                      | D-006         |
| A-007a | Refund flow: request (reason, amount) → approval by Accounts (configurable approver) → paid (method, reference, date). Refunds never edit or delete the original payment row.                                                                                                                       | D-007         |
| A-007b | **Full refund** of all verified payments ⇒ admission moves to `CANCELLED_REFUNDED`, batch seat is released, lead status becomes `CLOSED_LOST` with reason "Refunded". **Partial refund** reduces net revenue; admission stays confirmed.                                                            | D-007         |
| A-007c | Reports are event-dated: an admission cancelled in March still counts as an admission in January and as a cancellation in March. "Net admissions" = confirmed − cancelled in the period. Approved incentives are never silently recalculated; refunds create a clawback item for approval (FR-016). | D-007         |
| A-008  | Isolation: organization isolation enforced twice — application data-access layer **and** PostgreSQL row-level security on `organization_id`. Brand/team scope enforced in the application data-access layer and covered by API tests.                                                               | D-001         |
| A-009  | Lead owner does not change when counselling or admission work starts; counsellor and admission officer are added as lead participants.                                                                                                                                                              | SRS 2, FR-011 |
| A-010  | Default maximum automatic reassignment attempts = 3 (diagram: attempt 2 at 30 min, attempt 3 at 60 min), then manager priority queue. Previous owners of the same lead are excluded.                                                                                                                | FR-007        |
| A-011  | Default first-response rule: a logged call attempt resolves the 5- and 15-minute checkpoints; connected contact is tracked separately (contact rate). Changeable per brand.                                                                                                                         | SRS 14        |
| A-012  | Multi-currency reports show INR and AED separately. Consolidated cross-currency totals are not shown until an FX policy is decided.                                                                                                                                                                 | D-002         |

| A-013 | Email is globally unique across the platform (one login per person). | D-001 |
| A-014 | Platform Super Admin manages organizations (create, suspend, activate) but cannot read organization business data. | D-001 |
| A-015 | Passwords ≥ 10 characters; 5 failed logins lock the account for 15 minutes (both configurable by env). | SRS FR-002 |
| A-016 | Brand Managers may edit their own brand and manage branches/teams/users inside it; creating brands and custom roles requires organization-level scope. | SRS §2 |
| A-017 | Anti-escalation: a user can grant a role only if they hold every permission of that role at the target scope; the organization must always keep one active Organization Admin. | SRS §2.1 |

| A-018 | Default working week per brand: India Mon–Sat 09:30–18:30, UAE Mon–Fri 09:00–18:00 (brand time zone). Each brand can change shifts, add split shifts and holidays. | D-002, D-003 |
| A-019 | Default SLA ladder per brand from the diagram: remind 5, alert team leader 15 (= first-response target), reassign 30 and 60, escalate to manager 90; all on working minutes; max 3 automatic reassignments; same executive excluded for 24 h. Editable per brand. | FR-009 |
| A-020 | Course fees are stored in the brand's currency only (no multi-currency price lists yet). Full fee plans, discounts and instalments arrive in Phase 12. | D-002, FR-015 |

| A-021 | One person per normalized phone number (E.164) per organization; email matching is used only when no phone matches. Shared family phones are a Phase 5 duplicate-review case. | D-004, FR-005 |
| A-022 | A lead needs a name plus a valid phone or email. Local numbers use the brand's country (India +91, UAE +971). Unknown course codes or campaigns are kept as text, not rejected. | FR-004 |
| A-023 | Idempotency: provider/external ID, or a hash of the submission + calendar day. Identical resubmissions on the same day are treated as one; a repeat enquiry on a later day is recorded. | FR-004 |
| A-024 | Leads have no owner until Phase 6 allocation. A user with `lead.read_own` sees leads they own or entered personally. Marketing roles without `pii.view_full` see masked phones/emails. | FR-007, §2.1 |
| A-025 | Meta Lead Ads and WhatsApp connectors wait for the owner's Meta app / WhatsApp Business account (O-04, O-06). Until then Meta leads can arrive via the intake API (e.g. Zapier/Make) and are attributed with channel META_ADS through a Meta source key. | FR-003, rule 10 |

| A-026 | A new enquiry on the same active lead from a different channel within 24 hours is classified CROSS_CHANNEL_DUPLICATE (one ad click submitted twice); otherwise EXISTING_LEAD. A known person's first lead in another brand is EXISTING_PERSON. | FR-005 |
| A-027 | Duplicate suggestions score: same email 0.6, phone one digit/swap apart 0.5, same normalized name 0.3 (+0.1 same city), shared name word 0.15; ≥ 0.6 is suggested. A common name alone is never suggested. Dismissed pairs are never re-raised. Changing a phone to another person's number is refused and raises a SAME_PHONE suggestion. | FR-005 |
| A-028 | Merge keeps both person rows (the merged one marked, original IDs kept); where both have an active lead in a brand the older lead survives and the newer becomes MERGED. Enquiries are never modified. Merging requires `lead.merge` over every brand involved. Un-merge is not offered (history is preserved in `person_merges`). | FR-005 |
| A-029 | Only holders of `lead.receive` (Sales Executive template) are allocated leads; Organization Admin holds every permission except this one. Only grants tied to the lead's brand count (organization-wide grants never make someone a recipient). `lead.receive` may be granted by anyone holding `lead.assign` or `lead.reassign` at that scope. Users with no languages accept any language; empty capacity = no limit. | FR-007 |
| A-030 | Allocation runs right after a lead is created. Leads that cannot be placed (outside working hours, nobody eligible) wait in the unassigned queue; managers are notified once per lead. The queue is drained by a manager ("Allocate queued leads") and by each new lead of the brand; a timed drain every minute needs the always-on worker (Phase 7 — Vercel serverless has no background worker). Manual assignment needs a reason and may exceed capacity (recorded as over capacity). | FR-007 |
| A-031 | Next-action rule: an open lead must keep at least one open task; completing or cancelling the last one requires a next task in the same action. A hold (reason required, optional review date) replaces the next task and pauses the SLA. ASSUMED: no separate approval step for holds yet (any user who may edit the lead; audited). Hold time counts on neither SLA clock. | FR-008, §5.1 |
| A-032 | First response = completing a first-call or call-back task with any call outcome (A-011); "connected" is stored as the outcome and reported separately. Automatic (SLA) reassignment keeps the running ladder; a manual reassignment counts as an override and starts a fresh clock for the new owner. Open tasks follow the lead to the new owner. Merged leads stop their SLA and cancel open tasks. | FR-009 |
| A-033 | Background jobs use a PostgreSQL queue (`jobs`, deterministic keys, SKIP LOCKED, 5 attempts with backoff, then DEAD) instead of Redis/BullMQ, because the hosted API has no Redis and the job must commit with the business change. Run by an in-process worker (long-lived server) or the `/internal/tick` endpoint (serverless). | Rule 7 |
| A-034 | Business-initiated WhatsApp messages always use an approved template (provider rule outside the 24-hour reply window). Approval is recorded in the CRM by a user with `campaign.manage` or `settings.manage` after the provider approves it; editing an approved template's text sends it back to draft. Placeholders: first_name, full_name, course, owner_name, brand; a message with an empty placeholder is refused. | FR-010 |
| A-035 | Counselling appointments: a counsellor cannot be double-booked; reminder to counsellor and lead owner 60 minutes before; outcome = attended (summary) or no-show; cancel needs a reason. Any active user with a role in the brand can be booked as counsellor. | FR-010 |
| A-036 | Until providers are chosen (O-06), WhatsApp and click-to-call use labelled sandbox adapters in development/test only; production shows them as not configured and calls are logged manually. Email uses the SMTP mail service (no attachments until document storage, Phase 11). Inbound "STOP / UNSUBSCRIBE / OPT OUT" sets do-not-contact; do-not-contact blocks WhatsApp and email but not calls (shown as a warning). No call recordings are stored. | FR-010, rule 10 |
